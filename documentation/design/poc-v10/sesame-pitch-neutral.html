~35 s Sésame works in two conversations. The owner gives us the website they already have and a few sentences about how they work. We read the site, build a profile, and generate a dedicated agent: its own tables, time slots, policies and booking tools. Day to day, the owner runs it by chatting: block a slot, change the max party size, see tonight’s bookings. On the other side, the guest just talks to Claude. Claude finds the restaurant through Sésame, checks availability, asks for confirmation and books. No form anywhere.

One protocol between every agent and every restaurant

  1. Claude

    Guest’s assistant, one connector added once

  2. Sésame gateway

    MCP server: discovery, preference filters, routing

  3. Restaurant agent

    One per merchant: tables, slots, policies, tools

  4. PostgreSQL

    One isolated schema per restaurant

~30 s Under the hood: Claude connects once to our gateway, a remote MCP server. The gateway applies the guest’s preferences as filters, finds the restaurant and routes the call to that restaurant’s agent, which books in its own isolated database schema. Onboarding is a five step pipeline: crawl, extract, validate, provision, go live. And the website does not disappear: if an agent fails or takes more than two seconds, the guest gets a link to the restaurant’s own booking page. One presence serves agents and humans.

The core really works

  • No double booking

    Enforced by the database itself, tested with concurrent bookings.

  • Schema, never code

    The model only fills a validated profile. Tools and data are deterministic.

  • The guest always confirms

    Claude asks before every booking, change or cancellation.

  • Always a way out

    On error or after 2 s, the guest gets the restaurant’s own page.

  • Isolated per restaurant

    One database schema per merchant, hardened website crawler.

  • Live for the owner

    New bookings reach the owner’s chat in under 2 seconds.
