Broad Agent Transfer Protocol (BATP)

Abstract

This document specifies the Broad Agent Transfer Protocol (BATP), an application protocol reserved for software agents that book with merchants on behalf of people or businesses. A BATP session runs over TCP, starts with a handshake that names the calling agent, and carries newline-delimited JSON frames. Each request states an intent (discover merchants, check availability, book, amend, cancel, talk with the merchant's agent in natural language, recall bookings, ping) and the merchant it addresses. Responses carry numeric status codes and, when the merchant's own agent cannot serve the request, a fallback URL to the merchant's website. A write proposed in a conversation is carried out only once the caller confirms it. BATP is designed to sit behind a Model Context Protocol (MCP) server, which acts as a bridge for assistants that only speak MCP.¶

1. Introduction

Software agents increasingly act for people: they search for a restaurant, check a table and book it. When that traffic uses HTTP, a merchant cannot tell it apart from a browser, so it cannot identify the calling agent, route agent traffic separately, or apply rules meant for agents.¶

BATP gives that traffic its own channel. Every frame says which agent is talking (established once per session), what it intends to do, and to which merchant. The protocol is deliberately small: it covers what a network of merchant agents needs to take bookings, and nothing else.¶

This document defines version 0.2 of BATP. Version 0.2 adds one intent to version 0.1: TALK, with which a guest's agent talks with the merchant's agent in natural language (Section 8.6). The changes are listed in Appendix D.¶

1.1. Scope

This version covers the guest side of booking with restaurants: discovery, availability, booking, amending, cancelling and recalling a guest's bookings, and a conversation with the merchant's agent about any of these. Merchant-side operations (listing a day's bookings, blocking a slot, changing a policy) are out of scope: they stay on the merchant's own platform.¶

1.2. Relation to MCP

Assistants such as Claude connect to remote tools through MCP [MCP]. An MCP server can act as a bridge: each of its tools maps to one BATP intent (Appendix A). Any other agent can speak BATP directly.¶

1.3. Relation to AGTP

The idea of an application protocol reserved for agent traffic, with agent identity and intent-named methods, comes from the AGTP Internet-Draft [I-D.hood-independent-agtp]. BATP is independent from it: it does not implement AGTP, it uses a different transport framing and method set, and it is limited to the booking use case.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This document uses the Augmented Backus-Naur Form (ABNF) notation of [RFC5234]. JSON terminology ("object", "member", "string") is that of [RFC8259].¶

Node:

A BATP server. It serves the merchant agents of one backend.¶

Merchant agent:

One merchant's booking logic and data, served by a node and addressed by the merchant's slug. Since version 0.2, it also includes the conversational agent, built on a language model, that answers TALK (Section 8.6).¶

Caller:

An agent that opens a session with a node: a user's assistant, a merchant's agent, or a bridge acting for one of them.¶

Session:

One transport connection between a caller and a node, from the caller's hello to the connection's close.¶

Frame:

One JSON object followed by a line feed (Section 5).¶

Intent:

What a request asks the node to do, for example BOOK.¶

Slug:

The stable identifier of a merchant on a node: 3 to 61 characters among lowercase ASCII letters, digits and "-".¶

Guest:

The person a booking is for, identified in this version by the name the caller gives (see Section 13).¶

Conversation:

A sequence of TALK requests from one caller to one merchant agent, named by an opaque identifier that the node chooses (Section 8.6).¶

Proposal:

A write (a booking, a change or a cancellation) that a merchant agent offers in a conversation, and carries out only when a later TALK confirms it (Section 8.6).¶

3. Protocol Overview

A caller opens a TCP connection to a node and sends hello, naming itself. The node answers welcome, which opens the session, or reject, which closes it. The caller then sends requests. Each request carries an id, an intent, the addressed merchant when the intent needs one, and parameters. The node answers each request with exactly one response carrying the same id. Several requests may be in flight at once, and responses may arrive in any order.¶

In this example, the TALK takes longer than the DISCOVER sent after it, because the merchant's agent runs a model turn to answer it (Section 7.4).¶

4. Transport

BATP runs over TCP [RFC9293]. A node listens on a configured port. This document uses port 4710 for its examples and its reference implementation; that port is not registered for BATP (Section 14), so a caller MUST be able to use another port.¶

On the loopback interface, a session MAY use plain TCP. On any other path, the caller and the node MUST use TLS 1.3 [RFC9846] or a later version, and the caller MUST authenticate the node's certificate against the host name it connected to. TLS is set up before the first frame.¶

Either side MAY close the connection at any time. Closing the connection ends the session. A request in flight when the session ends has no response, and the caller MUST NOT assume it was or was not carried out (see Section 7.7 for retrying writes safely).¶

4.1. Addressing

A merchant agent is named by a URI [RFC3986] of the form:¶

batp-URI = "batp://" host [ ":" port ] "/" slug
slug     = 3*61( %x61-7A / DIGIT / "-" )   ; a-z, 0-9, "-"
¶

where host and port are those of [RFC3986]. When port is absent, it is 4710. For example, batp://node.example/le-petit-zinc names the merchant agent le-petit-zinc on the node at node.example. The slug is not sent in the handshake: a session reaches every merchant agent of a node, and each request names its merchant (Section 7).¶

5. Framing

Every message is a frame: one JSON object [RFC8259], encoded in UTF-8 [RFC3629], followed by one line feed (%x0A).¶

frame = object LF
LF    = %x0A
¶

The rule object, and the rules it uses, are those of [RFC8259], Sections 2 to 7, with one change: inside a frame, the rule ws is¶

ws = *( %x20 / %x09 )   ; space or tab, never LF or CR
¶

so that a frame never contains a line feed before its end. A line feed inside a string is escaped as \n, as JSON requires.¶

  • A frame, without its final LF, MUST NOT exceed 65536 octets. A node that has read 65536 octets of a frame without finding its LF MUST send an error frame with status 413 (Section 7.6) and close the session, without parsing the frame.¶

  • The object MUST have a member type whose value is a string. The types defined in this version are hello, welcome, reject, request, response and error. The type event is reserved (Section 10).¶

  • A sender MUST NOT generate an object with two members of the same name. A receiver MAY treat such a frame as invalid.¶

  • A receiver MUST ignore members of a frame that this document does not define for its type (Section 11). This rule applies to the frame object itself, not to params (Section 7).¶

  • An empty line (an LF alone) is not a frame. A node MUST ignore it.¶

6. Session

The caller speaks first. Its first frame MUST be a hello. Until the node has sent welcome, the caller MUST NOT send any other frame, and a node that receives one MUST answer reject with status 400 and close the session.¶

6.1. hello

Table 1: Members of hello
Member Type Requirement
type "hello" REQUIRED
batp version string (Section 11) REQUIRED
agent object, below REQUIRED
token string see below
Table 2: Members of hello.agent
Member of agent Type Requirement
id string, 1 to 256 characters REQUIRED
name string OPTIONAL, for display and logs
kind "user-agent" or "merchant-agent" REQUIRED
operator string OPTIONAL, who runs the agent

  • agent.id names the calling agent. The node treats it as an opaque string and attributes every request of the session to it. This document uses identifiers of the form urn:batp:agent:<name>; batp is not a registered URN namespace [RFC8141], so these identifiers are only meaningful between parties that agreed on them.¶

  • agent.kind is user-agent when the caller acts for a guest, and merchant-agent when it acts for a business.¶

  • token is the caller's credential on this node, issued out of band. A node MUST refuse a hello from a non-loopback peer that has no token. A node MAY accept a hello without token on the loopback interface.¶

The node MUST answer a hello with exactly one welcome or reject.¶

6.2. welcome

Table 3: Members of welcome
Member Type Requirement

batp the version of the session (Section 11) REQUIRED
node object with id (string, REQUIRED) and name (string, OPTIONAL) REQUIRED
intents array of the intent names the node serves in this session REQUIRED
session string, the node's identifier for this session REQUIRED

intents lists only intents that the session's version defines: in a session of version 0.1, a node that speaks 0.2 does not list TALK (Section 11). A caller MUST NOT send a request whose intent is not in intents. A node that receives one MUST answer it with status 400 and code invalid_input, without carrying it out.¶

6.3. reject

Table 4: Members of reject
Member Type Requirement
type "reject" REQUIRED
status 400, 401 or 426 REQUIRED
message string, for humans REQUIRED
batp the version the node speaks OPTIONAL

  • 401: the agent is unknown to the node, the token is missing where it is required, or the token does not match the agent.¶

  • 426: the node does not speak the major version in hello.batp (Section 11). The node SHOULD include batp.¶

  • 400: the first frame was not a valid hello.¶

After sending reject, the node MUST close the connection.¶

7. Requests and Responses

7.1. request

Table 5: Members of request
Member Type Requirement
type "request" REQUIRED
id string, 1 to 64 characters REQUIRED
intent intent name (Section 8) REQUIRED
merchant slug REQUIRED for AVAILABILITY, BOOK, AMEND, CANCEL and TALK; absent otherwise
params object REQUIRED ({} when the intent takes none)

  • The caller chooses id. It MUST be unique among the requests of the session that have not been answered yet. A node that receives a request whose id is already in flight MUST send an error frame with status 400 and MUST NOT carry out the request.¶

  • params MUST validate against the intent's params schema (Appendix C). Unlike frame members, unknown members of params are invalid: a node MUST answer status 400 with code invalid_input.¶

  • A request for an intent that needs merchant and lacks it, or for an intent that takes none and has it, MUST be answered with status 400.¶

7.2. response

Table 6: Members of response
Member Type Requirement
type "response" REQUIRED
id the request's id REQUIRED
status status code (Section 9) REQUIRED
result object present if and only if status is 200
error object, below present if and only if status is not 200
Table 7: Members of response.error
Member of error Type Requirement
code error code (Section 9) REQUIRED
message string, for the guest or the caller REQUIRED
fallback_url absolute URI REQUIRED for party_too_large and agent_unavailable; absent otherwise

  • A node MUST send exactly one response to each request it accepted, unless the session ends first.¶

  • result MUST validate against the intent's result schema (Appendix C).¶

  • fallback_url is the merchant's own booking page. A caller SHOULD give it to the guest, so that the guest can still book when the merchant agent cannot serve the request.¶

  • message MUST NOT contain stack traces or internal identifiers (Section 12).¶

7.3. Concurrency

A caller MAY send a request before earlier ones are answered. A node MAY carry out the requests of one session concurrently, and MAY answer them in any order. A caller MUST match responses to requests by id only.¶

A node MUST accept at least 32 requests in flight per session. A node MAY answer a request beyond its limit with status 429 and code too_many_requests, without carrying it out. The request itself is valid: the caller MAY send it again once one of its earlier requests has been answered.¶

7.4. Deadlines

A node SHOULD answer a TALK within 25 seconds of receiving it, and a request of any other intent within 10 seconds. A TALK gets longer because the merchant's agent answers it with a model turn and the tool calls that turn makes (Section 8.6).¶

A node that has not carried out a request by the deadline it applies MUST answer it with status 503 and code agent_unavailable (Section 9), rather than leave it unanswered. A caller SHOULD wait for the answer to a TALK at least as long as the node's deadline for TALK, so that the guest gets the node's answer, or its fallback_url, rather than the caller's own timeout. A caller that stops waiting for a request before its answer MUST NOT assume that the request was or was not carried out.¶

7.5. Idle sessions

A node SHOULD close a session that has received no frame for 60 seconds, and MUST NOT close it for idleness sooner. A caller that wants to keep a session open sends PING (Section 8.8).¶

7.6. Session errors

An error frame reports a problem that no response can carry because no request id can be attributed: the frame is not JSON, has no valid type or id, is too large, or reuses an id in flight.¶

Table 8: Members of error
Member Type Requirement
type "error" REQUIRED
status 400 or 413 REQUIRED
message string REQUIRED

After an error frame with status 413, the node closes the session. After one with status 400, the session stays open. A node that receives a frame of an unknown type MUST send an error frame with status 400. A caller that receives a frame of an unknown type MUST ignore it, so that later versions can add frames sent by the node (Section 10).¶

7.7. Idempotency

A write sent again after a lost session must not book twice.¶

  • BOOK, AMEND and TALK carry params.idempotency_key, chosen by the caller. A caller retrying one of them MUST reuse the key of the first attempt, with the same params, and SHOULD use a fresh unpredictable key for every new write and every new TALK message.¶

  • For BOOK, the key is scoped to the merchant. A node that receives a BOOK with a key already used at that merchant, and the same starts_at, party_size and guest, MUST return status 200 with the reservation the first request created, and MUST NOT create another. If the params differ, it MUST answer status 400 with code invalid_input.¶

  • For AMEND, the key is scoped to the merchant too. A node that receives an AMEND with a key it already applied, for the same booking and the same starts_at and party_size, MUST NOT change the booking again and MUST return it as it is now, with status 200: a late retry never undoes a later change. If the booking or the params differ, it MUST answer status 400 with code invalid_input. An AMEND that failed does not use up its key.¶

  • CANCEL is idempotent without a key: cancelling a booking already cancelled by the guest returns it again, with status 200.¶

  • For TALK, the key is scoped to the merchant and to the session's agent.id. A node that receives a TALK with a key it already answered with status 200, for that merchant and that agent.id, MUST return the result it returned then, with status 200, without calling its model again and without carrying out any write. A TALK answered with another status does not use up its key.¶

  • TALK is not read-only: it can carry out a write (Section 8.6). A client library MUST NOT send a TALK again by itself after a lost session, as it may for DISCOVER, AVAILABILITY, RECALL and PING; the caller decides, and retries with the same key.¶

7.8. Confirmation before writes

BOOK, AMEND and CANCEL change a guest's plans. A caller acting for a guest MUST obtain the guest's explicit confirmation of the merchant, time, party size and name before sending any of them. A node cannot verify this; it is a requirement on callers, and a bridge enforces it through what it tells the assistant (Appendix A).¶

In a TALK conversation, the same requirement applies to confirm: a caller acting for a guest MUST NOT send confirm before the guest explicitly accepted the proposal's summary, after the caller showed it to them. A "yes" given before the proposal was shown does not count. Here the node enforces the other half: it carries out a proposed write only on a confirm that names it (Section 8.6.1).¶

8. Intents

Times are RFC 3339 [RFC3339] date-time values with an explicit offset. date is an RFC 3339 full-date and time is HH:MM (24-hour clock), both in the merchant's local time zone. The params and result of each intent are defined by the JSON Schemas of Appendix C; this section states their meaning and errors.¶

Table 9: BATP 0.2 intents
Intent merchant Purpose
DISCOVER absent Find merchants matching a query and preferences
AVAILABILITY required Up to 3 start times with a free table
BOOK required Create a booking
AMEND required Move a booking or change its party size
CANCEL required Cancel a booking as the guest
TALK required Talk with the merchant's agent in natural language (since 0.2)
RECALL absent A guest's upcoming bookings and notices
PING absent Liveness check, keeps the session open

8.1. DISCOVER

Params: query (string), and optionally near (string), date, and filters with tags (array of strings) and max_price: one to four EURO SIGN characters (U+20AC), from "€" (cheapest) to "€€€€".¶

Result: merchants, the live merchants matching the query and all filters, each with slug, name, city, tags, price_level and website. When filters exclude every merchant, suggestions lists which filter to drop (drop) and how many merchants would then match (matches). ignored_filters lists the tags the node does not know.¶

A caller MUST send the guest's preferences as filters. A node MUST NOT store them beyond the request.¶

Errors: 400.¶

8.2. AVAILABILITY

Params: date, party_size (integer, at least 1), and optionally time.¶

Result: slots, at most 3, each with starts_at and table_label. When time is given, the node returns the start times closest to it (the earlier one at equal distance); otherwise, the earliest ones. Start times already past are never returned. The result is sorted by starts_at. An empty slots array means nothing is free that day for that party.¶

Errors: 400, 404, 413, 503.¶

8.3. BOOK

Params: starts_at, party_size, guest_name (non-empty string), idempotency_key (non-empty string).¶

Result: reservation, with id (the merchant's reference, for example "R-001"), merchant, starts_at, party_size, table_label, status ("confirmed"), guest_name and via.¶

via is the booking channel, as the merchant sees it. Versions 0.1 and 0.2 define "claude", "merchant" and "website"; "website" is never set by BATP. The same rule applies to a booking made through TALK (Section 8.6). A node MUST record "merchant" when the caller's agent.kind is merchant-agent, and "claude" when it is user-agent, whatever assistant the caller is. So in this version, via is only accurate for callers behind the reference bridge (Section 12). A later version may add a value for other assistants.¶

starts_at MUST be a start time the merchant offers; AVAILABILITY returns such times. Errors: 400, 404, 409, 413, 503.¶

8.4. AMEND

Params: reservation_id, guest_name, idempotency_key, and at least one of starts_at and party_size.¶

The booking MUST be confirmed and MUST belong to guest_name; otherwise the node answers 404, without saying which check failed. Result: reservation, as amended.¶

Errors: 400, 404, 409, 413, 503.¶

8.5. CANCEL

Params: reservation_id, guest_name. The same ownership rule as AMEND applies. Result: reservation, with status "cancelled".¶

Errors: 400, 404, 503.¶

8.6. TALK

TALK is defined since version 0.2. A node MUST NOT offer or serve it in a session of version 0.1 (Section 11).¶

With TALK, a guest's agent talks with the merchant's agent in natural language: it passes on what the guest wants, with the guest's preferences, and the merchant's agent answers. To answer, the merchant's agent can check availability, look up the guest's bookings at this merchant, and propose a booking, a change or a cancellation. It carries out a proposal only when the caller confirms it in a later TALK (Section 8.6.1).¶

Params:¶

  • message (REQUIRED): what the caller says to the merchant's agent. Once leading and trailing white space is removed, it MUST be 1 to 2000 characters long, and it MUST NOT contain a control character (Unicode general category Cc) other than LF (U+000A).¶

  • idempotency_key (REQUIRED): as for BOOK, with the same bounds (Section 7.7).¶

  • conversation: absent on the first message of a conversation. On every later message, the conversation that the node returned (Section 8.6.2).¶

  • confirm: the id of the conversation's pending proposal, sent to have it carried out. A caller MUST send it only after the guest's explicit confirmation (Section 7.8). A TALK with confirm MUST also carry conversation; a node answers one without it with status 400 and code invalid_input.¶

Conversation and proposal identifiers are opaque to the caller, and follow this rule:¶

opaque-id = 1*64( ALPHA / DIGIT / "_" / "-" )
¶

As for every intent, unknown params are invalid (Section 7).¶

Result:¶

  • conversation: the conversation's identifier, an opaque-id: a new one on the first message, the one the caller sent on later messages.¶

  • reply: the merchant agent's answer, at most 2000 characters. It is the only member written by the agent's language model. A caller SHOULD relay it to the guest. A caller MUST NOT take reply as proof that anything was booked, changed or cancelled: only reservation says so.¶

The other members are built by the node's code from the results of the tools that the merchant's agent called, never from the model's text, so that a caller can rely on them:¶

  • slots: the start times the agent found free while answering, each as in the result of AVAILABILITY; an empty array when it found none or did not look.¶

  • pending: the write the agent proposes, or null. It has id (an opaque-id), action ("book", "change" or "cancel"), summary (1 to 500 characters, built by code from the proposal's own arguments, for the caller to show the guest) and expires_at (an RFC 3339 date-time with an offset). A conversation has at most one pending proposal: a new one replaces the previous one.¶

  • reservation: the booking that a write carried out by this TALK created, changed or cancelled, as in the result of BOOK; null when this TALK carried out no write.¶

  • fallback_url: the merchant's own booking page, set when the agent cannot serve what the guest asked, for example after one of its tools refused it (Section 8.6.3); null otherwise.¶

  • tools_called: the names of the tools the agent called while answering, in the order of the calls, without their arguments or results. When a confirm carried out a proposal, it also names the write the node's code ran (for example "create_reservation"), although the model has no tool that writes (Section 8.6.1). Each name is 1 to 64 characters: a lowercase ASCII letter, then lowercase ASCII letters, digits and "_".¶

conversation and reply are always present. A caller handles an absent pending, reservation or fallback_url as null, and an absent slots or tools_called as an empty array.¶

8.6.1. Proposals and confirmation

The merchant's agent has no tool that writes: a booking, a change or a cancellation is first a proposal, returned in pending.¶

  • A node MUST NOT carry out a write proposed in a conversation until a later TALK of the same conversation names the proposal's id in confirm, before its expires_at. The node's code MUST enforce this, whatever the model outputs and whatever the message says: a message that says "yes" without confirm carries out nothing.¶

  • On a TALK whose confirm names the conversation's pending proposal before it expires, the node carries out that proposal with the arguments stored with it, before it calls the model, so that neither the message nor the model's output can change what is written.¶

  • A node MUST carry out a proposal at most once, even when the TALK that confirms it is sent again under another key.¶

  • A confirm that names no pending proposal of the conversation (unknown, replaced or expired) carries out no write. The node answers it with status 200, and reply says that nothing was done.¶

  • If the write fails when it is carried out, for example because the time was taken in the meantime, nothing is written and the proposal is gone. The node answers with status 200; the agent MAY offer other times in a new proposal, which needs a new confirmation.¶

  • When this TALK carried out a write, the node MUST set reservation, even if its model fails afterwards.¶

8.6.2. Conversations

  • A node MUST choose each conversation at random, with at least 128 bits of entropy, and SHOULD choose each pending.id in the same way.¶

  • A node binds a conversation, when it creates it, to the merchant and to the session's agent.id. It MUST answer status 404 to a TALK whose conversation is unknown, has expired, or was created for another merchant or another agent.id, without saying which.¶

  • A conversation is not tied to a BATP session: a caller MAY continue it in a later session under the same agent.id, for example after a lost session. A bridge carries the conversations of all its users on one session, under one agent.id (Appendix A), so only the unguessable identifier separates them.¶

  • A node MAY expire a conversation, for example after a period without messages, or lose it when it restarts. A caller that gets status 404 for a conversation MAY start a new one, without conversation.¶

8.6.3. Status

Status 200 means that the merchant's agent answered, whatever the answer, including a refusal such as "we are full". When one of the agent's tools refuses, for example with party_too_large or slot_unavailable, the refusal goes to the model, which words it in reply, and the node's code sets fallback_url: the TALK still gets status 200. Any other status means that the agent could not answer:¶

  • 400 invalid_input: invalid params, confirm without conversation, or a TALK in a session of version 0.1.¶

  • 404 not_found: the merchant is unknown or not yet live, or the conversation is unknown, has expired, or belongs to another merchant or another agent.id.¶

  • 429 too_many_requests: too many requests in flight in the session (Section 7.3). A node MAY also answer 429, without calling its model, to a TALK beyond the limits it sets on model use, such as the model turns running at once or the TALK requests a merchant receives per minute. The caller MAY send it again later, with the same key.¶

  • 503 agent_unavailable, with fallback_url: the merchant is marked as down, the agent failed, or it did not answer by its deadline (Section 7.4).¶

Errors: 400, 404, 429, 503.¶

8.7. RECALL

Params: guest_name.¶

Result: reservations, the guest's upcoming confirmed bookings at every live merchant of the node, and notices, messages for the guest (for example, that a merchant cancelled a booking). A node MUST return a notice in every RECALL for the guest during 24 hours after the first RECALL that returned it, and MUST NOT return it after that. An answer lost on its way to the caller therefore loses no notice if the next RECALL comes within those 24 hours, and a caller MAY send a RECALL again. A caller SHOULD NOT show the guest a notice it already showed them.¶

Errors: 400, 503.¶

8.8. PING

Params: {}. Result: pong (true) and server_time, the node's clock.¶

Errors: none defined.¶

9. Status Codes

Table 10: BATP 0.2 status codes
Status error.code Meaning fallback_url
200 none Success no
400 invalid_input Invalid params, unknown intent or one the session's version does not define, missing or unexpected merchant no
401 none hello refused (in reject only) no
404 not_found Unknown merchant, merchant not yet live, unknown booking, a booking that is not the guest's, or an unknown or expired conversation no
409 slot_unavailable The time is taken, blocked, in the past, or not one the merchant offers no
413 party_too_large The party is above the merchant's online limit, or no table fits it yes
426 none Unsupported major version (in reject only) no
429 too_many_requests Too many requests in flight in the session, or a TALK beyond the node's limits; retry later no
503 agent_unavailable The merchant agent is down, failed, or did not answer by its deadline yes

The status values 400 and 413 also appear in error frames (Section 7.6), which carry no error.code; there, 413 means a frame above the size limit.¶

A node MUST answer 503 to AVAILABILITY, BOOK, AMEND, CANCEL and TALK when the merchant is marked as down, without consulting the merchant agent (for TALK, without calling its model). A caller that gets 413 or 503 MUST NOT retry the same request to the same merchant in a loop; it SHOULD offer the guest the fallback_url.¶

A caller that receives a status it does not know MUST handle it as the class of its first digit: 2 as success, 4 as a caller error, 5 as a node error.¶

10. Events

Frames of type event, sent by the node without a request, are reserved for a later minor version: version 0.2 does not define them. One intended use is to tell a guest's agent that a merchant cancelled a booking; in this version, that reaches the guest as a notice returned by RECALL. A caller of version 0.1 or 0.2 ignores them (Section 7.6).¶

11. Versioning and Extensibility

A version is written major.minor:¶

version = 1*DIGIT "." 1*DIGIT
¶

This document defines version 0.2. Version 0.2 adds TALK to version 0.1, and changes nothing that version 0.1 defined.¶

In hello, the caller sends the highest version it speaks. If the node speaks the same major version, it answers welcome with the highest minor version both speak, which is the lower of the caller's minor version and its own, and both sides use that version for the session. Otherwise it answers reject with status 426. A node speaks every earlier minor version of its major version, since each one only adds to the previous one. For example, a node of version 0.2 answers a hello with "batp": "0.1" with a welcome with "batp": "0.1", and the session is a session of version 0.1.¶

A node MUST NOT list in welcome.intents an intent that the session's version does not define, and MUST answer a request for one with status 400 and code invalid_input (Section 6.2). In a session of version 0.1, a node of version 0.2 therefore neither offers nor serves TALK, and a caller of version 0.1 keeps working unchanged.¶

Within a major version, a later minor version MAY add intents, optional frame members, optional params, result members and status codes: adding an intent, as version 0.2 does with TALK, is a minor change. It MUST NOT change the meaning of what an earlier minor version defined. Because unknown params members are invalid (Section 7), a caller MUST NOT send params that the session's version does not define. A caller MUST ignore result members it does not know.¶

12. Security Considerations

Agent identity and tokens:

The node attributes every request to the agent.id of its session. That attribution is only as good as the token check: a node MUST bind each token to one agent.id and refuse a hello whose token does not match. A node SHOULD compare tokens in constant time. Tokens MUST NOT be sent outside TLS except on the loopback interface, and SHOULD be long random strings that a node can revoke individually.¶

Transport:

Without TLS, anyone on the path reads guest names, bookings and tokens, and can change them. Section 4 therefore requires TLS 1.3 off the loopback interface. A node bound to the loopback interface is reachable by every local process: deployments on shared hosts SHOULD still require tokens.¶

Limits and denial of service:

The frame size limit, the limit on requests in flight and the idle timeout bound what one session costs a node. A node SHOULD also limit sessions per peer and per agent. A node MUST stop reading a frame at the size limit instead of buffering it. A TALK costs a model turn, which is far more expensive than any other request: a node SHOULD bound the model turns it runs at once and the TALK requests each merchant receives per unit of time, and answer 429 beyond them without calling its model (Section 8.6.3).¶

Booking channel:

In this version, as in version 0.1, a node records every user-agent booking with via "claude" (Section 8), and the merchant is told the booking came through Claude. With other assistants, that is wrong. A merchant SHOULD read via as "an assistant" until a later version names the calling agent in it.¶

Writes without confirmation:

A misbehaving caller can book, amend or cancel without asking the guest. The node cannot detect it. Idempotency keys prevent duplicate bookings on retries, not unwanted ones. Through TALK, a node does enforce that a write follows a confirm naming a proposal it returned (Section 8.6.1), but it still cannot tell whether the caller asked the guest before sending confirm.¶

A language model reading untrusted text:

The merchant's agent that answers TALK is a language model, and message is text it cannot trust: the guest's agent may relay anything that a person or a web page told it, including instructions written to make the model book, cancel or reveal data (prompt injection). A node therefore relies on its code, not on the model's instructions, for everything below.¶

Confirmation of writes in code:

A write proposed through TALK runs only on a later confirm that names its proposal before it expires, with the arguments stored with the proposal (Section 8.6.1). This check MUST be made by the node's code, never left to the model: the model has no tool that writes, so no output of the model alone can create, change or cancel a booking.¶

Tools and merchant binding:

The merchant's agent MUST only be given the guest-side operations of its own merchant (checking availability, finding the guest's bookings at that merchant, and proposing a booking, a change or a cancellation), never merchant-side operations such as listing a day's bookings or blocking a slot. The merchant MUST be bound by the node's code, from the request's merchant, and MUST NOT be an argument of any tool the model fills in, so that one merchant's agent cannot read or change another merchant's data, whatever the model is told.¶

Website content:

The text crawled from the merchant's website MUST NOT enter the agent's prompt as such. Only data validated against a schema and reviewed by the merchant before publishing may, and the agent's prompt marks it as data, not instructions: it was still taken from a website, which anyone who can edit that website controls.¶

Conversation identifiers:

A conversation identifier is a capability: with it, and the token of the agent.id it is bound to, a caller can continue the conversation and confirm its proposal. A node MUST make it unguessable and bind it to the merchant and the agent.id (Section 8.6.2). A node and a bridge MUST NOT log conversation identifiers together with guest names at a level enabled in production, and SHOULD log a digest of the identifier rather than the identifier itself.¶

Model output:

reply is written by a model and can be wrong. A caller MUST NOT tell the guest that a booking was made, changed or cancelled unless reservation says so. Before asking the guest to confirm, a caller SHOULD show them pending.summary, which the node's code builds from the proposal itself.¶

Guest identity:

In this version, a booking belongs to whoever gives its guest name and reference. Any authenticated caller that knows both can amend or cancel it, and RECALL returns the bookings of any name. This is acceptable only in an experiment with trusted callers. A deployment beyond that needs guest authentication, which a later version would define.¶

Error messages:

error.message reaches people. A node MUST NOT put stack traces, internal names or data of other guests in it.¶

Fallback URLs:

A caller passes fallback_url to a person. A caller SHOULD only offer https URLs, and a node SHOULD only send URLs on the merchant's own website.¶

13. Privacy Considerations

Guest names:

Guest names and party sizes are personal data. A node SHOULD NOT write guest names to logs at a level enabled in production. The reference implementation logs, for each request, the agent id, intent, merchant, status and latency, and nothing that names the guest.¶

Preferences:

DISCOVER filters can reveal diet or religion (vegan, halal, kosher). A node MUST NOT store them beyond the request or link them to a guest.¶

Conversations:

TALK messages and replies are free text, and may carry guest names, preferences such as diet or religion, and anything else the guest said. The same rule as for guest names applies: a node and a bridge SHOULD NOT write message or reply to logs at a level enabled in production. Unlike DISCOVER filters, which a node does not keep, a conversation keeps what was said in it for as long as the node keeps the conversation: a node SHOULD keep a conversation no longer than it accepts messages in it, and SHOULD NOT link it to a guest beyond it. A node that shows its merchant the requests it received shows the merchant what the guest's agent said.¶

Recall:

As Section 12 says, RECALL returns the bookings of any name it is given, and for 24 hours the notices too: a notice names the merchant, the booking and its date. Callers SHOULD only send the name of the guest they act for.¶

Agent identity:

agent.id identifies software, not a person. A caller SHOULD NOT put personal data in it.¶

Appendix A. The MCP Bridge

An MCP server can let an assistant that only speaks MCP use a BATP node. The reference bridge opens one session with agent.id urn:batp:agent:claude-gateway and agent.kind user-agent, and maps its tools to intents:¶

Table 11: MCP tools and BATP intents
MCP tool BATP intent Notes
search_merchants DISCOVER  
get_availability AVAILABILITY the tool's merchant becomes the request's merchant
create_reservation BOOK idem
update_reservation AMEND idem
cancel_reservation CANCEL the tool returns {"status": "cancelled"}
talk_to_merchant TALK the tool's merchant becomes the request's merchant
get_my_reservations RECALL  

For TALK, the bridge has one tool, talk_to_merchant(merchant, message, idempotency_key, conversation?, confirm?), whose arguments other than merchant become the params of TALK, and whose result is the result of TALK. In this version, the four booking tools (get_availability, create_reservation, update_reservation and cancel_reservation) stay mapped to their intents as above, until a later version closes the direct intents to guests' agents in favor of TALK.¶

  • The tool descriptions tell the assistant to confirm with the guest before create_reservation, update_reservation and cancel_reservation, which is how the bridge meets the confirmation requirement of Section 7.8. The description of talk_to_merchant tells it to relay reply, to show pending.summary and ask the guest when pending is set, to send confirm only after the guest's explicit yes, and to give the guest any fallback_url.¶

  • The bridge answers each tool call within 2 seconds, including the round trip to the node, except talk_to_merchant, which it gives 30 seconds: longer than the node's deadline for TALK (Section 7.4), so that the node's 503 and its fallback_url arrive before the bridge gives up. A timeout, a lost session or a 503 becomes an agent_unavailable tool error with the merchant's fallback_url.¶

  • The bridge carries the conversations of all its users on its one session, under one agent.id: only the conversation identifier, which the node makes unguessable (Section 8.6.2), keeps one user from continuing another's conversation. A 404 for an unknown or expired conversation is a not_found tool error, not an outage: the assistant starts a new conversation.¶

  • A status and its error object become the tool error {"error": code, "message": ..., "fallback_url": ...}. too_many_requests is not a tool error code: the bridge stays under the limit on requests in flight, and reports any 429, including one for a TALK beyond the node's limits on model use, as agent_unavailable.¶

Appendix B. Example Session

The caller is the MCP bridge. Lines starting with "C:" go from the caller to the node, and lines starting with "N:" from the node to the caller. Long frames are wrapped here for readability: on the wire, each is one line.¶

The caller then books, and checks a larger party while the booking is in flight: the second answer arrives first.¶

Another guest asks, in the same session, for a table on another day. The caller talks with the merchant's agent: a first message, which opens a conversation, then the guest's choice, which the agent turns into a proposal.¶

The caller shows the guest the proposal's summary. Once the guest has said yes, the caller confirms the proposal, and the node books the table with the proposal's own arguments, before its model words the answer.¶

Appendix D. Changes from Version 0.1

  • Added the TALK intent (Section 8.6), with its conversations and its proposals, which the node carries out only on confirm; TALK is addressed, so merchant is required for it.¶

  • Stated how the session's version is chosen, and that a session of version 0.1 is neither offered nor served TALK (Section 11).¶

  • Added deadlines for answering requests: 25 seconds for TALK, 10 seconds for the other intents (Section 7.4).¶

  • Added TALK to the idempotency rules, and said that a client library does not send a TALK again by itself (Section 7.7).¶

  • Moved the reservation of event frames to a later minor version (Section 10).¶

  • Added the bridge's talk_to_merchant tool (Appendix A).¶

  • Added the security and privacy considerations of a merchant agent built on a language model (Section 12, Section 13).¶
