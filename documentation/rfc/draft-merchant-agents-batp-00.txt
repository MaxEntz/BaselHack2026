                  Broad Agent Transfer Protocol (BATP)
                     draft-merchant-agents-batp-00

Abstract

   This document specifies the Broad Agent Transfer Protocol (BATP), an
   application protocol reserved for software agents that book with
   merchants on behalf of people or businesses.  A BATP session runs
   over TCP, starts with a handshake that names the calling agent, and
   carries newline-delimited JSON frames.  Each request states an intent
   (discover merchants, check availability, book, amend, cancel, recall
   bookings, ping) and the merchant it addresses.  Responses carry
   numeric status codes and, when the merchant's own agent cannot serve
   the request, a fallback URL to the merchant's website.  BATP is
   designed to sit behind a Model Context Protocol (MCP) server, which
   acts as a bridge for assistants that only speak MCP.

1.  Introduction

   Software agents increasingly act for people: they search for a
   restaurant, check a table and book it.  When that traffic uses HTTP,
   a merchant cannot tell it apart from a browser, so it cannot identify
   the calling agent, route agent traffic separately, or apply rules
   meant for agents.

   BATP gives that traffic its own channel.  Every frame says which
   agent is talking (established once per session), what it intends to
   do, and to which merchant.  The protocol is deliberately small: it
   covers what a network of merchant agents needs to take bookings, and
   nothing else.

1.1.  Scope

   This version covers the guest side of booking with restaurants:
   discovery, availability, booking, amending, cancelling and recalling
   a guest's bookings.  Merchant-side operations (listing a day's
   bookings, blocking a slot, changing a policy) are out of scope: they
   stay on the merchant's own platform.

1.2.  Relation to MCP

   Assistants such as Claude connect to remote tools through MCP [MCP].
   An MCP server can act as a bridge: each of its tools maps to one BATP
   intent (Appendix A).  Any other agent can speak BATP directly.

1.3.  Relation to AGTP

   The idea of an application protocol reserved for agent traffic, with
   agent identity and intent-named methods, comes from the AGTP
   Internet-Draft [I-D.hood-independent-agtp].  BATP is independent from
   it: it does not implement AGTP, it uses a different transport framing
   and method set, and it is limited to the booking use case.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This document uses the Augmented Backus-Naur Form (ABNF) notation of
   [RFC5234].  JSON terminology ("object", "member", "string") is that
   of [RFC8259].

   Node:  A BATP server.  It serves the merchant agents of one backend.

   Merchant agent:  One merchant's booking logic and data, served by a
      node and addressed by the merchant's slug.

   Caller:  An agent that opens a session with a node: a user's
      assistant, a merchant's agent, or a bridge acting for one of them.

   Session:  One transport connection between a caller and a node, from
      the caller's hello to the connection's close.

   Frame:  One JSON object followed by a line feed (Section 5).

   Intent:  What a request asks the node to do, for example BOOK.

   Slug:  The stable identifier of a merchant on a node: 3 to 61
      characters among lowercase ASCII letters, digits and "-".

   Guest:  The person a booking is for, identified in this version by
      the name the caller gives (see Section 13).

3.  Protocol Overview

   A caller opens a TCP connection to a node and sends hello, naming
   itself.  The node answers welcome, which opens the session, or
   reject, which closes it.  The caller then sends requests.  Each
   request carries an id, an intent, the addressed merchant when the
   intent needs one, and parameters.  The node answers each request with
   exactly one response carrying the same id.  Several requests may be
   in flight at once, and responses may arrive in any order.

   user's        +-------------+   MCP over HTTPS   +-------------+
   assistant --->| MCP client  |------------------->| MCP gateway |
                 +-------------+                    |  (bridge)   |
                                                    +------+------+
                                                           | BATP
   other agent ------------------- BATP --------------+    | TCP 4710
                                                      v    v
                                                    +-------------+
                                                    |  BATP node  |
                                                    +------+------+
                                                           |
                                          merchant agents (one per slug)

4.  Transport

   BATP runs over TCP [RFC9293].  A node listens on a configured port.
   This document uses port 4710 for its examples and its reference
   implementation; that port is not registered for BATP (Section 14), so
   a caller MUST be able to use another port.




                           Expires 4 May 2027                   [Page 5]

Internet-Draft                    BATP                      October 2026


   On the loopback interface, a session MAY use plain TCP.  On any other
   path, the caller and the node MUST use TLS 1.3 [RFC9846] or a later
   version, and the caller MUST authenticate the node's certificate
   against the host name it connected to.  TLS is set up before the
   first frame.

   Either side MAY close the connection at any time.  Closing the
   connection ends the session.  A request in flight when the session
   ends has no response, and the caller MUST NOT assume it was or was
   not carried out (see Section 7.6 for retrying writes safely).

4.1.  Addressing

   A merchant agent is named by a URI [RFC3986] of the form:

   batp-URI = "batp://" host [ ":" port ] "/" slug
   slug     = 3*61( %x61-7A / DIGIT / "-" )   ; a-z, 0-9, "-"

   where host and port are those of [RFC3986].  When port is absent, it
   is 4710.  For example, batp://node.example/le-petit-zinc names the
   merchant agent le-petit-zinc on the node at node.example.  The slug
   is not sent in the handshake: a session reaches every merchant agent
   of a node, and each request names its merchant (Section 7).

5.  Framing

   Every message is a frame: one JSON object [RFC8259], encoded in UTF-8
   [RFC3629], followed by one line feed (%x0A).

   frame = object LF
   LF    = %x0A

   The rule object, and the rules it uses, are those of [RFC8259],
   Sections 2 to 7, with one change: inside a frame, the rule ws is

   ws = *( %x20 / %x09 )   ; space or tab, never LF or CR

   so that a frame never contains a line feed before its end.  A line
   feed inside a string is escaped as \n, as JSON requires.

   *  A frame, without its final LF, MUST NOT exceed 65536 octets.  A
      node that has read 65536 octets of a frame without finding its LF
      MUST send an error frame with status 413 (Section 7.5) and close
      the session, without parsing the frame.

   *  The object MUST have a member type whose value is a string.  The
      types defined in this version are hello, welcome, reject, request,
      response and error.  The type event is reserved (Section 10).



                           Expires 4 May 2027                   [Page 6]

Internet-Draft                    BATP                      October 2026


   *  A sender MUST NOT generate an object with two members of the same
      name.  A receiver MAY treat such a frame as invalid.

   *  A receiver MUST ignore members of a frame that this document does
      not define for its type (Section 11).  This rule applies to the
      frame object itself, not to params (Section 7).

   *  An empty line (an LF alone) is not a frame.  A node MUST ignore
      it.

6.  Session

   The caller speaks first.  Its first frame MUST be a hello.  Until the
   node has sent welcome, the caller MUST NOT send any other frame, and
   a node that receives one MUST answer reject with status 400 and close
   the session.

7.3.  Concurrency

   A caller MAY send a request before earlier ones are answered.  A node
   MAY carry out the requests of one session concurrently, and MAY
   answer them in any order.  A caller MUST match responses to requests
   by id only.

   A node MUST accept at least 32 requests in flight per session.  A
   node MAY answer a request beyond its limit with status 429 and code
   too_many_requests, without carrying it out.  The request itself is
   valid: the caller MAY send it again once one of its earlier requests
   has been answered.

7.4.  Idle sessions

   A node SHOULD close a session that has received no frame for 60
   seconds, and MUST NOT close it for idleness sooner.  A caller that
   wants to keep a session open sends PING (Section 8.7).

7.5.  Session errors

   An error frame reports a problem that no response can carry because
   no request id can be attributed: the frame is not JSON, has no valid
   type or id, is too large, or reuses an id in flight.

                  +=========+============+=============+
                  | Member  | Type       | Requirement |
                  +=========+============+=============+
                  | type    | "error"    | REQUIRED    |
                  +---------+------------+-------------+
                  | status  | 400 or 413 | REQUIRED    |
                  +---------+------------+-------------+
                  | message | string     | REQUIRED    |
                  +---------+------------+-------------+

                        Table 8: Members of error

   After an error frame with status 413, the node closes the session.
   After one with status 400, the session stays open.  A node that
   receives a frame of an unknown type MUST send an error frame with
   status 400.  A caller that receives a frame of an unknown type MUST
   ignore it, so that later versions can add frames sent by the node
   (Section 10).

7.6.  Idempotency

   A write sent again after a lost session must not book twice.

   *  BOOK and AMEND carry params.idempotency_key, chosen by the caller.
      A caller retrying a write MUST reuse the key of the first attempt,
      with the same params, and SHOULD use a fresh unpredictable key for
      every new write.

   *  For BOOK, the key is scoped to the merchant.  A node that receives
      a BOOK with a key already used at that merchant, and the same
      starts_at, party_size and guest, MUST return status 200 with the
      reservation the first request created, and MUST NOT create
      another.  If the params differ, it MUST answer status 400 with
      code invalid_input.





                           Expires 4 May 2027                  [Page 12]

Internet-Draft                    BATP                      October 2026


   *  For AMEND, the key is scoped to the merchant too.  A node that
      receives an AMEND with a key it already applied, for the same
      booking and the same starts_at and party_size, MUST NOT change the
      booking again and MUST return it as it is now, with status 200: a
      late retry never undoes a later change.  If the booking or the
      params differ, it MUST answer status 400 with code invalid_input.
      An AMEND that failed does not use up its key.

   *  CANCEL is idempotent without a key: cancelling a booking already
      cancelled by the guest returns it again, with status 200.

7.7.  Confirmation before writes

   BOOK, AMEND and CANCEL change a guest's plans.  A caller acting for a
   guest MUST obtain the guest's explicit confirmation of the merchant,
   time, party size and name before sending any of them.  A node cannot
   verify this; it is a requirement on callers, and a bridge enforces it
   through what it tells the assistant (Appendix A).

8.  Intents

   Times are RFC 3339 [RFC3339] date-time values with an explicit
   offset. date is an RFC 3339 full-date and time is HH:MM (24-hour
   clock), both in the merchant's local time zone.  The params and
   result of each intent are defined by the JSON Schemas of Appendix C;
   this section states their meaning and errors.

8.1.  DISCOVER

   Params: query (string), and optionally near (string), date, and
   filters with tags (array of strings) and max_price: one to four EURO
   SIGN characters (U+20AC), from "€" (cheapest) to "€€€€".

   Result: merchants, the live merchants matching the query and all
   filters, each with slug, name, city, tags, price_level and website.
   When filters exclude every merchant, suggestions lists which filter
   to drop (drop) and how many merchants would then match (matches).
   ignored_filters lists the tags the node does not know.

   A caller MUST send the guest's preferences as filters.  A node MUST
   NOT store them beyond the request.

   Errors: 400.

8.2.  AVAILABILITY

   Params: date, party_size (integer, at least 1), and optionally time.





                           Expires 4 May 2027                  [Page 14]

Internet-Draft                    BATP                      October 2026


   Result: slots, at most 3, each with starts_at and table_label.  When
   time is given, the node returns the start times closest to it (the
   earlier one at equal distance); otherwise, the earliest ones.  Start
   times already past are never returned.  The result is sorted by
   starts_at.  An empty slots array means nothing is free that day for
   that party.

   Errors: 400, 404, 413, 503.

8.3.  BOOK

   Params: starts_at, party_size, guest_name (non-empty string),
   idempotency_key (non-empty string).

   Result: reservation, with id (the merchant's reference, for example
   "R-001"), merchant, starts_at, party_size, table_label, status
   ("confirmed"), guest_name and via.

   via is the booking channel, as the merchant sees it.  Version 0.1
   defines "claude", "merchant" and "website"; "website" is never set by
   BATP.  A node MUST record "merchant" when the caller's agent.kind is
   merchant-agent, and "claude" when it is user-agent, whatever
   assistant the caller is.  So in this version, via is only accurate
   for callers behind the reference bridge (Section 12).  A later
   version may add a value for other assistants.

   starts_at MUST be a start time the merchant offers; AVAILABILITY
   returns such times.  Errors: 400, 404, 409, 413, 503.

8.4.  AMEND

   Params: reservation_id, guest_name, idempotency_key, and at least one
   of starts_at and party_size.

   The booking MUST be confirmed and MUST belong to guest_name;
   otherwise the node answers 404, without saying which check failed.
   Result: reservation, as amended.

   Errors: 400, 404, 409, 413, 503.

8.5.  CANCEL

   Params: reservation_id, guest_name.  The same ownership rule as AMEND
   applies.  Result: reservation, with status "cancelled".

   Errors: 400, 404, 503.





                           Expires 4 May 2027                  [Page 15]

Internet-Draft                    BATP                      October 2026


8.6.  RECALL

   Params: guest_name.

   Result: reservations, the guest's upcoming confirmed bookings at
   every live merchant of the node, and notices, messages for the guest
   (for example, that a merchant cancelled a booking).  A node MUST
   return a notice in every RECALL for the guest during 24 hours after
   the first RECALL that returned it, and MUST NOT return it after that.
   An answer lost on its way to the caller therefore loses no notice if
   the next RECALL comes within those 24 hours, and a caller MAY send a
   RECALL again.  A caller SHOULD NOT show the guest a notice it already
   showed them.

   Errors: 400, 503.

8.7.  PING

   Params: {}. Result: pong (true) and server_time, the node's clock.

   Errors: none defined.

10.  Events

   Frames of type event, sent by the node without a request, are
   reserved for a later version.  One intended use is to tell a guest's
   agent that a merchant cancelled a booking; in this version, that
   reaches the guest as a notice returned by RECALL.  A 0.1 caller
   ignores them (Section 7.5).

11.  Versioning and Extensibility

   A version is written major.minor:

   version = 1*DIGIT "." 1*DIGIT

   This document defines version 0.1.  In hello, the caller sends the
   highest version it speaks.  If the node speaks the same major
   version, it answers welcome with the highest minor version both
   speak, and both sides use that version for the session.  Otherwise it
   answers reject with status 426.

   Within a major version, a later minor version MAY add intents,
   optional frame members, optional params, result members and status
   codes.  It MUST NOT change the meaning of what an earlier minor
   version defined.  Because unknown params members are invalid
   (Section 7), a caller MUST NOT send params that the session's version
   does not define.  A caller MUST ignore result members it does not
   know.

12.  Security Considerations

   Agent identity and tokens:  The node attributes every request to the
      agent.id of its session.  That attribution is only as good as the
      token check: a node MUST bind each token to one agent.id and
      refuse a hello whose token does not match.  A node SHOULD compare
      tokens in constant time.  Tokens MUST NOT be sent outside TLS
      except on the loopback interface, and SHOULD be long random
      strings that a node can revoke individually.

   Transport:  Without TLS, anyone on the path reads guest names,
      bookings and tokens, and can change them.  Section 4 therefore
      requires TLS 1.3 off the loopback interface.  A node bound to the
      loopback interface is reachable by every local process:
      deployments on shared hosts SHOULD still require tokens.

   Limits and denial of service:  The frame size limit, the limit on
      requests in flight and the idle timeout bound what one session
      costs a node.  A node SHOULD also limit sessions per peer and per
      agent.  A node MUST stop reading a frame at the size limit instead
      of buffering it.

   Booking channel:  In version 0.1, a node records every user-agent
      booking with via "claude" (Section 8), and the merchant is told
      the booking came through Claude.  With other assistants, that is
      wrong.  A merchant SHOULD read via as "an assistant" until a later
      version names the calling agent in it.




                           Expires 4 May 2027                  [Page 18]

Internet-Draft                    BATP                      October 2026


   Writes without confirmation:  A misbehaving caller can book, amend or
      cancel without asking the guest.  The node cannot detect it.
      Idempotency keys prevent duplicate bookings on retries, not
      unwanted ones.

   Guest identity:  In this version, a booking belongs to whoever gives
      its guest name and reference.  Any authenticated caller that knows
      both can amend or cancel it, and RECALL returns the bookings of
      any name.  This is acceptable only in an experiment with trusted
      callers.  A deployment beyond that needs guest authentication,
      which a later version would define.

   Error messages:  error.message reaches people.  A node MUST NOT put
      stack traces, internal names or data of other guests in it.

   Fallback URLs:  A caller passes fallback_url to a person.  A caller
      SHOULD only offer https URLs, and a node SHOULD only send URLs on
      the merchant's own website.

13.  Privacy Considerations

   Guest names:  Guest names and party sizes are personal data.  A node
      SHOULD NOT write guest names to logs at a level enabled in
      production.  The reference implementation logs, for each request,
      the agent id, intent, merchant, status and latency, and nothing
      that names the guest.

   Preferences:  DISCOVER filters can reveal diet or religion (vegan,
      halal, kosher).  A node MUST NOT store them beyond the request or
      link them to a guest.

   Recall:  As Section 12 says, RECALL returns the bookings of any name
      it is given, and for 24 hours the notices too: a notice names the
      merchant, the booking and its date.  Callers SHOULD only send the
      name of the guest they act for.

   Agent identity:  agent.id identifies software, not a person.  A
      caller SHOULD NOT put personal data in it.
