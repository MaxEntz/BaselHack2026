                  Broad Agent Transfer Protocol (BATP)
                     draft-merchant-agents-batp-00

Abstract

   This document specifies the Broad Agent Transfer Protocol (BATP), an
   application protocol reserved for software agents that book with
   merchants on behalf of people or businesses.  A BATP session runs
   over TCP, starts with a handshake that names the calling agent, and
   carries newline-delimited JSON frames.  Each request states an
   intent: discover merchants, talk with a merchant's agent in natural
   language, recall a guest's bookings, or ping.  A caller checks
   availability and books, changes or cancels a booking only by talking
   with the merchant's agent, which proposes each write and carries it
   out only once the caller confirms it.  Responses carry numeric status
   codes and, when the merchant's agent cannot serve the request, a
   fallback URL to the merchant's website.  BATP is designed to sit
   behind a Model Context Protocol (MCP) server, which acts as a bridge
   for assistants that only speak MCP.

1.  Introduction

   Software agents increasingly act for people: they search for a
   restaurant, check a table and book it.  When that traffic uses HTTP,
   a merchant cannot tell it apart from a browser, so it cannot identify
   the calling agent, route agent traffic separately, or apply rules
   meant for agents.

   BATP gives that traffic its own channel.  Every frame says which
   agent is talking (established once per session), what it intends to
   do, and, when it addresses one, to which merchant.  The protocol is
   deliberately small: it covers what a network of merchant agents needs
   to take bookings, and nothing else.

   This document defines version 0.3 of BATP.  Version 0.2 added TALK,
   with which a guest's agent talks with the merchant's agent in natural
   language (Section 8.2).  Version 0.3 removes the four intents with
   which a caller checked availability and booked, changed or cancelled
   directly: a caller now does all of that through TALK.  Only the
   merchant's agent, under the control of the node's code, uses the
   merchant's booking operations, and every write follows a proposal
   that the node built and a confirmation that names it, whoever the
   caller is.  The changes are listed in Appendix D.

1.1.  Scope

   This version covers the guest side of booking with restaurants:
   discovering merchants, a conversation with the merchant's agent to
   check availability and to book, change or cancel a booking, and
   recalling a guest's bookings.  Merchant-side operations (listing a
   day's bookings, blocking a slot, changing a policy) are out of scope:
   they stay on the merchant's own platform.

1.2.  Relation to MCP

   Assistants such as Claude connect to remote tools through MCP [MCP].
   An MCP server can act as a bridge: each of its tools maps to one BATP
   intent (Appendix A).  Any other agent can speak BATP directly.

1.3.  Relation to AGTP

   The idea of an application protocol reserved for agent traffic, with
   agent identity and intent-named methods, comes from the AGTP
   Internet-Draft [I-D.hood-independent-agtp].  BATP is independent from
   it: it does not implement AGTP, it uses a different transport framing
   and method set, and it is limited to the booking use case.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This document uses the Augmented Backus-Naur Form (ABNF) notation of
   [RFC5234].  JSON terminology ("object", "member", "string") is that
   of [RFC8259].

   Node:  A BATP server.  It serves the merchant agents of one backend.

   Merchant agent:  One merchant's booking logic and data, served by a
      node and addressed by the merchant's slug, together with the
      conversational agent, built on a language model, that answers TALK
      for that merchant (Section 8.2).  Since version 0.3, that
      conversational agent is the only way a caller reaches the
      merchant's booking operations.

   Caller:  An agent that opens a session with a node: a user's
      assistant, a merchant's agent, or a bridge acting for one of them.

   Session:  One transport connection between a caller and a node, from
      the caller's hello to the connection's close.

   Frame:  One JSON object followed by a line feed (Section 5).

   Intent:  What a request asks the node to do, for example TALK.

   Slug:  The stable identifier of a merchant on a node: 3 to 61
      characters among lowercase ASCII letters, digits and "-".

   Guest:  The person a booking is for, identified in this version by
      the name the caller gives (see Section 13).

   Conversation:  A sequence of TALK requests from one caller to one
      merchant agent, named by an opaque identifier that the node
      chooses (Section 8.2).

   Proposal:  A write (a booking, a change or a cancellation) that a
      merchant agent offers in a conversation, and carries out only when
      a later TALK confirms it (Section 8.2).

3.  Protocol Overview

   A caller opens a TCP connection to a node and sends hello, naming
   itself.  The node answers welcome, which opens the session, or
   reject, which closes it.  The caller then sends requests.  Each
   request carries an id, an intent, the addressed merchant when the
   intent needs one, and parameters.  The node answers each request with
   exactly one response carrying the same id.  Several requests may be
   in flight at once, and responses may arrive in any order.

   assistant --->| MCP client  |------------------->| MCP gateway |
                 +-------------+                    |  (bridge)   |
                                                    +------+------+
                                                           | BATP
   other agent ------------------- BATP --------------+    | TCP 4710
                                                      v    v
                                                    +-------------+
                                                    |  BATP node  |
                                                    +------+------+
                                                           |
                                          merchant agents (one per slug)

4.  Transport

   BATP runs over TCP [RFC9293].  A node listens on a configured port.
   This document uses port 4710 for its examples and its reference
   implementation; that port is not registered for BATP (Section 14), so
   a caller MUST be able to use another port.

   On the loopback interface, a session MAY use plain TCP.  On any other
   path, the caller and the node MUST use TLS 1.3 [RFC9846] or a later
   version, and the caller MUST authenticate the node's certificate
   against the host name it connected to.  TLS is set up before the
   first frame.

   Either side MAY close the connection at any time.  Closing the
   connection ends the session.  A request in flight when the session
   ends has no response, and the caller MUST NOT assume it was or was
   not carried out (see Section 7.7 for retrying a TALK safely).

4.1.  Addressing

   A merchant agent is named by a URI [RFC3986] of the form:

   batp-URI = "batp://" host [ ":" port ] "/" slug
   slug     = 3*61( %x61-7A / DIGIT / "-" )   ; a-z, 0-9, "-"






                           Expires 5 May 2027                   [Page 6]

Internet-Draft                    BATP                     November 2026


   where host and port are those of [RFC3986].  When port is absent, it
   is 4710.  For example, batp://node.example/le-petit-zinc names the
   merchant agent le-petit-zinc on the node at node.example.  The slug
   is not sent in the handshake: a session reaches every merchant agent
   of a node, and each request names its merchant (Section 7).

5.  Framing

   Every message is a frame: one JSON object [RFC8259], encoded in UTF-8
   [RFC3629], followed by one line feed (%x0A).

   frame = object LF
   LF    = %x0A

   The rule object, and the rules it uses, are those of [RFC8259],
   Sections 2 to 7, with one change: inside a frame, the rule ws is

   ws = *( %x20 / %x09 )   ; space or tab, never LF or CR

   so that a frame never contains a line feed before its end.  A line
   feed inside a string is escaped as \n, as JSON requires.

   *  A frame, without its final LF, MUST NOT exceed 65536 octets.  A
      node that has read 65536 octets of a frame without finding its LF
      MUST send an error frame with status 413 (Section 7.6) and close
      the session, without parsing the frame.

   *  The object MUST have a member type whose value is a string.  The
      types defined in this version are hello, welcome, reject, request,
      response and error.  The type event is reserved (Section 10).

   *  A sender MUST NOT generate an object with two members of the same
      name.  A receiver MAY treat such a frame as invalid.

   *  A receiver MUST ignore members of a frame that this document does
      not define for its type (Section 11).  This rule applies to the
      frame object itself, not to params (Section 7).

   *  An empty line (an LF alone) is not a frame.  A node MUST ignore
      it.

6.  Session

   The caller speaks first.  Its first frame MUST be a hello.  Until the
   node has sent welcome, the caller MUST NOT send any other frame, and
   a node that receives one MUST answer reject with status 400 and close
   the session.

7.3.  Concurrency

   A caller MAY send a request before earlier ones are answered.  A node
   MAY carry out the requests of one session concurrently, and MAY
   answer them in any order.  A caller MUST match responses to requests
   by id only.

   A node MUST accept at least 32 requests in flight per session.  A
   node MAY answer a request beyond its limit with status 429 and code
   too_many_requests, without carrying it out.  The request itself is
   valid: the caller MAY send it again once one of its earlier requests
   has been answered.

7.4.  Deadlines

   A node SHOULD answer a TALK within 25 seconds of receiving it, and a
   request of any other intent within 10 seconds.  A TALK gets longer
   because the merchant's agent answers it with a model turn and the
   tool calls that turn makes (Section 8.2).

   A node that has not carried out a request by the deadline it applies
   MUST answer it with status 503 and code agent_unavailable
   (Section 9), rather than leave it unanswered.  A caller SHOULD wait
   for the answer to a TALK at least as long as the node's deadline for
   TALK, so that the guest gets the node's answer, or its fallback_url,
   rather than the caller's own timeout.  A caller that stops waiting
   for a request before its answer MUST NOT assume that the request was
   or was not carried out.

7.5.  Idle sessions

   A node SHOULD close a session that has received no frame for 60
   seconds, and MUST NOT close it for idleness sooner.  A caller that
   wants to keep a session open sends PING (Section 8.4).

7.6.  Session errors

   An error frame reports a problem that no response can carry because
   no request id can be attributed: the frame is not JSON, has no valid
   type or id, is too large, or reuses an id in flight.

7.7.  Idempotency

   A message sent again after a lost session must not book twice.  In
   this version, only TALK can carry out a write (Section 8.2.2):
   DISCOVER, RECALL and PING change nothing.

   *  TALK carries params.idempotency_key, chosen by the caller.  A
      caller retrying a TALK MUST reuse the key of the first attempt,
      with the same params, and SHOULD use a fresh unpredictable key for
      every new message.

   *  The key is scoped to the merchant, the session's agent.id and the
      conversation; the key of a first message, which names no
      conversation yet, is scoped to the merchant and the agent.id.  A
      node that receives a TALK with a key it already answered with
      status 200 in that scope, with the same message, conversation and
      confirm, MUST return the result it returned then, with status 200,
      without calling its model again and without carrying out any
      write.  If one of them differs, the node MUST answer status 400
      with code invalid_input, without carrying out anything.  A TALK
      answered with another status does not use up its key.

   *  The node cannot tell a retry from another guest of the same caller
      who sends the same message with the same key.  A caller that
      carries the messages of several guests under one agent.id, as a
      bridge does (Appendix A), MUST therefore choose keys that they
      cannot guess.





                           Expires 5 May 2027                  [Page 13]

Internet-Draft                    BATP                     November 2026


   *  A confirmed proposal has its own protection: the node carries it
      out at most once, whatever key the TALK that confirms it carries
      (Section 8.2.1).

   *  TALK is not read-only.  A client library MUST NOT send a TALK
      again by itself after a lost session, as it may for DISCOVER,
      RECALL and PING; the caller decides, and retries with the same
      key.

7.8.  Confirmation before writes

   A booking, a change or a cancellation changes a guest's plans.  In
   this version, a caller can only obtain one through TALK, and the
   node's code carries it out only on a confirm that names a proposal
   the node returned, before the proposal expires (Section 8.2.1).  This
   holds for every caller, whatever it declared in hello.

   What the node cannot check is that the guest agreed.  A caller acting
   for a guest MUST NOT send confirm before the guest explicitly
   accepted the proposal's summary, after the caller showed it to them.
   A "yes" given before the proposal was shown does not count.

8.1.  DISCOVER

8.2.  TALK

   TALK is defined since version 0.2.  A node MUST NOT offer or serve it
   in a session of version 0.1 (Section 11).

   With TALK, a guest's agent talks with the merchant's agent in natural
   language: it passes on what the guest wants, with the guest's
   preferences, and the merchant's agent answers.  To answer, the
   merchant's agent can check availability, look up the guest's bookings
   at this merchant, and propose a booking, a change or a cancellation.
   It carries out a proposal only when the caller confirms it in a later
   TALK (Section 8.2.1).  Since version 0.3, TALK is the only intent
   with which a caller can book, change or cancel.

   Params:

   *  message (REQUIRED): what the caller says to the merchant's agent.
      Once leading and trailing white space is removed, it MUST be 1 to
      2000 characters long, and it MUST NOT contain a control character
      (Unicode general category Cc) other than LF (U+000A).

   *  idempotency_key (REQUIRED): a string of 1 to 200 characters,
      chosen by the caller (Section 7.7).




                           Expires 5 May 2027                  [Page 15]

Internet-Draft                    BATP                     November 2026


   *  conversation: absent on the first message of a conversation.  On
      every later message, the conversation that the node returned
      (Section 8.2.3).

   *  confirm: the id of the conversation's pending proposal, sent to
      have it carried out.  A caller MUST send it only after the guest's
      explicit confirmation (Section 7.8).  A TALK with confirm MUST
      also carry conversation; a node answers one without it with status
      400 and code invalid_input.

   Conversation and proposal identifiers are opaque to the caller, and
   follow this rule:

   opaque-id = 1*64( ALPHA / DIGIT / "_" / "-" )

   As for every intent, unknown params are invalid (Section 7).

   Result:

   *  conversation: the conversation's identifier, an opaque-id: a new
      one on the first message, the one the caller sent on later
      messages.

   *  reply: the merchant agent's answer, at most 2000 characters.  It
      is the only member written by the agent's language model.  A
      caller SHOULD relay it to the guest.  A caller MUST NOT take reply
      as proof that anything was booked, changed or cancelled: only
      reservation says so.

   The other members are built by the node's code from the results of
   the tools that the merchant's agent called, never from the model's
   text, so that a caller can rely on them:

   *  slots: the start times the agent found free in its last check of
      availability while answering, sorted by starts_at, each with
      starts_at and table_label (the table that start time would get);
      an empty array when it found none or did not look.  A slot is not
      held: another guest may take it before a proposal for it is
      confirmed.

   *  pending: the write the agent proposes, or null.  It has id (an
      opaque-id), action ("book", "change" or "cancel"), summary (1 to
      500 characters, built by code from the proposal's own arguments,
      for the caller to show the guest) and expires_at (an RFC 3339
      date-time with an offset).  A conversation has at most one pending
      proposal: a new one replaces the previous one.





                           Expires 5 May 2027                  [Page 16]

Internet-Draft                    BATP                     November 2026


   *  reservation: the booking that a write carried out by this TALK
      created, changed or cancelled (Section 8.2.2), with id (the
      merchant's reference, for example "R-001"), merchant, starts_at,
      party_size, table_label, status ("confirmed" or "cancelled"),
      guest_name and via; null when this TALK carried out no write.

   *  fallback_url: the merchant's own booking page, set when the agent
      cannot serve what the guest asked, for example after one of its
      tools refused it (Section 8.2.4); null otherwise.

   *  tools_called: the names of the tools the agent called while
      answering, in the order of the calls, without their arguments or
      results.  On a TALK whose confirm names the conversation's pending
      proposal, the first name is that of the write the node's code ran
      or tried for it (Section 8.2.2), although the model did not call
      it.  Each name is 1 to 64 characters: a lowercase ASCII letter,
      then lowercase ASCII letters, digits and "_".

   conversation and reply are always present.  A caller handles an
   absent pending, reservation or fallback_url as null, and an absent
   slots or tools_called as an empty array.

8.2.1.  Proposals and confirmation

   The merchant's agent has no tool that writes: a booking, a change or
   a cancellation is first a proposal, returned in pending.

   *  A node MUST NOT carry out a write proposed in a conversation until
      a later TALK of the same conversation names the proposal's id in
      confirm, before its expires_at.  The node's code MUST enforce
      this, whatever the model outputs and whatever the message says: a
      message that says "yes" without confirm carries out nothing.

   *  On a TALK whose confirm names the conversation's pending proposal
      before it expires, the node carries out that proposal with the
      arguments stored with it, before it calls the model, so that
      neither the message nor the model's output can change what is
      written.

   *  A node MUST carry out a proposal at most once, even when the TALK
      that confirms it is sent again under another key.

   *  A confirm that names no pending proposal of the conversation
      (unknown, replaced or expired) carries out no write.  The node
      answers it with status 200, and reply says that nothing was done.






                           Expires 5 May 2027                  [Page 17]

Internet-Draft                    BATP                     November 2026


   *  If the write fails when it is carried out, for example because the
      time was taken in the meantime, nothing is written and the
      proposal is gone.  The node answers with status 200; the agent MAY
      offer other times in a new proposal, which needs a new
      confirmation.

   *  When this TALK carried out a write, the node MUST set reservation,
      even if its model fails afterwards.

8.2.2.  Writes

   A confirmed proposal runs one of the merchant's booking operations,
   with the arguments stored with the proposal.  Its action says which:

   *  "book" creates a booking for the proposal's start time, party size
      and guest name.  A node MUST NOT create it unless the start time
      is one the merchant offers and a table that fits the party is free
      at that time when the write runs; the node chooses the table.  The
      write is named "create_reservation" in tools_called.

   *  "change" moves a booking, changes its party size, or both, with
      the same conditions for the new start time and party size.  It is
      named "update_reservation".

   *  "cancel" cancels a booking, as the guest.  It is named
      "cancel_reservation".

   A change or a cancellation applies only to an upcoming confirmed
   booking at this merchant, under the guest name given in the proposal,
   and only before the booking starts.  The merchant's agent cannot
   propose one otherwise, and the node does not say which of these
   conditions failed.

   via is the booking channel, as the merchant sees it.  Versions 0.1 to
   0.3 define "claude", "merchant" and "website"; "website" is never set
   by BATP.  A node MUST record a booking that a TALK creates with via
   "claude", whatever agent.kind the session declared: the caller
   declares its kind, and its token does not prove it, so the node does
   not trust it.  A change or a cancellation keeps the booking's via.
   In this version, via therefore names the channel rather than the
   calling assistant (Section 12); a later version may add a value for
   other assistants.

8.2.3.  Conversations

   *  A node MUST choose each conversation at random, with at least 128
      bits of entropy, and SHOULD choose each pending.id in the same
      way.



                           Expires 5 May 2027                  [Page 18]

Internet-Draft                    BATP                     November 2026


   *  A node binds a conversation, when it creates it, to the merchant
      and to the session's agent.id.  It MUST answer status 404 to a
      TALK whose conversation is unknown, has expired, or was created
      for another merchant or another agent.id, without saying which.

   *  A conversation is not tied to a BATP session: a caller MAY
      continue it in a later session under the same agent.id, for
      example after a lost session.  A bridge carries the conversations
      of all its users on one session, under one agent.id (Appendix A),
      so only the unguessable identifier separates them.

   *  A node MAY expire a conversation, for example after a period
      without messages or once it has had a number of messages, or lose
      it when it restarts.  A caller that gets status 404 for a
      conversation MAY start a new one, without conversation.

8.2.4.  Status

   Status 200 means that the merchant's agent answered, whatever the
   answer, including a refusal such as "we are full".  When one of the
   agent's tools refuses, for example because the time is taken or the
   party is above the merchant's online limit, the refusal goes to the
   model, which words it in reply.  When the agent cannot serve the
   request at all, as for a party above that limit, the node's code also
   sets fallback_url.  The TALK still gets status 200: since version
   0.3, no request is answered with status 409 or 413 (Section 9).  Any
   other status means that the agent could not answer:

   *  400 invalid_input: invalid params, confirm without conversation, a
      key already used with other params (Section 7.7), or a TALK in a
      session of version 0.1.

   *  404 not_found: the merchant is unknown or not yet live, or the
      conversation is unknown, has expired, or belongs to another
      merchant or another agent.id.

   *  429 too_many_requests: too many requests in flight in the session
      (Section 7.3).  A node MAY also answer 429, without calling its
      model, to a TALK beyond the limits it sets on model use, such as
      the model turns running at once or the TALK requests a merchant
      receives per minute.  The caller MAY send it again later, with the
      same key.

   *  503 agent_unavailable, with fallback_url: the merchant is marked
      as down, the agent failed, or it did not answer by its deadline
      (Section 7.4).

   Errors: 400, 404, 429, 503.



                           Expires 5 May 2027                  [Page 19]

Internet-Draft                    BATP                     November 2026


8.3.  RECALL

   Params: guest_name.

   Result: reservations, the guest's upcoming confirmed bookings at
   every live merchant of the node, each as reservation in the result of
   TALK (Section 8.2), and notices, messages for the guest (for example,
   that a merchant cancelled a booking).  A node MUST return a notice in
   every RECALL for the guest during 24 hours after the first RECALL
   that returned it, and MUST NOT return it after that.  An answer lost
   on its way to the caller therefore loses no notice if the next RECALL
   comes within those 24 hours, and a caller MAY send a RECALL again.  A
   caller SHOULD NOT show the guest a notice it already showed them.

   Errors: 400, 503.

8.4.  PING

   Params: {}. Result: pong (true) and server_time, the node's clock.

   Errors: none defined.

10.  Events

   Frames of type event, sent by the node without a request, are
   reserved for a later minor version: version 0.3 does not define them.
   One intended use is to tell a guest's agent that a merchant cancelled
   a booking; in this version, that reaches the guest as a notice
   returned by RECALL.  A caller of versions 0.1 to 0.3 ignores them
   (Section 7.6).

11.  Versioning and Extensibility

   A version is written major.minor:

   version = 1*DIGIT "." 1*DIGIT

   This document defines version 0.3.  Version 0.2 added TALK to version
   0.1.  Version 0.3 removes AVAILABILITY, BOOK, AMEND and CANCEL
   (Section 8), and records every booking made through TALK with via
   "claude", where version 0.2 recorded "merchant" for a caller that
   declared itself a merchant-agent (Section 8.2.2).  Its other changes
   state more precisely what version 0.2 defined for TALK (Appendix D).

   In hello, the caller sends the highest version it speaks.  If the
   node speaks the same major version, it answers welcome with the
   highest minor version both speak, which is the lower of the caller's
   minor version and its own, and both sides use that version for the
   session.  Otherwise it answers reject with status 426.  A node speaks
   every earlier minor version of its major version: a session of an
   earlier version gets the intents that version defined, less those
   that the node's version removed.  For example, a node of version 0.3
   answers a hello with "batp": "0.1" with a welcome with "batp": "0.1",
   and the session is a session of version 0.1, whose intents are
   DISCOVER, RECALL and PING.

   A node MUST NOT list in welcome.intents an intent that the session's
   version does not define or that the node's version removed, and MUST
   answer a request for one with status 400 and code invalid_input
   (Section 6.2).  In a session of version 0.1, a node of version 0.3
   therefore offers and serves neither TALK nor the removed intents: a
   caller of version 0.1 can still discover merchants and recall
   bookings, but can no longer book.  In a session of version 0.2 or
   0.3, it offers DISCOVER, TALK, RECALL and PING.

   Within a major version, a later minor version MAY add intents,
   optional frame members, optional params, result members and status
   codes: adding an intent, as version 0.2 did with TALK, is a minor
   change.  It MUST NOT change the meaning of what an earlier minor
   version defined.  While the major version is 0, a minor version MAY



                           Expires 5 May 2027                  [Page 22]

Internet-Draft                    BATP                     November 2026


   also remove intents, as version 0.3 does, and correct a rule of an
   earlier minor version, as version 0.3 does for via.  Removing an
   intent is not backward compatible: a caller that relied on it can no
   longer use it.  It is accepted only because version 0 is
   experimental; from version 1.0, it would need a new major version.  A
   node answers a removed intent as an unknown one, with status 400 and
   code invalid_input.  Because unknown params members are invalid
   (Section 7), a caller MUST NOT send params that the session's version
   does not define.  A caller MUST ignore result members it does not
   know.

12.  Security Considerations

   Agent identity and tokens:  The node attributes every request to the
      agent.id of its session.  That attribution is only as good as the
      token check: a node MUST bind each token to one agent.id and
      refuse a hello whose token does not match.  A node SHOULD compare
      tokens in constant time.  Tokens MUST NOT be sent outside TLS
      except on the loopback interface, and SHOULD be long random
      strings that a node can revoke individually.  A token proves
      agent.id only: agent.kind is the caller's claim, and a node does
      not grant or record anything on the strength of it
      (Section 8.2.2).

   Transport:  Without TLS, anyone on the path reads guest names,
      bookings and tokens, and can change them.  Section 4 therefore
      requires TLS 1.3 off the loopback interface.  A node bound to the
      loopback interface is reachable by every local process:
      deployments on shared hosts SHOULD still require tokens.

   Limits and denial of service:  The frame size limit, the limit on
      requests in flight and the idle timeout bound what one session
      costs a node.  A node SHOULD also limit sessions per peer and per
      agent.  A node MUST stop reading a frame at the size limit instead
      of buffering it.  A TALK costs a model turn, which is far more
      expensive than any other request: a node SHOULD bound the model
      turns it runs at once and the TALK requests each merchant receives
      per unit of time, and answer 429 beyond them without calling its
      model (Section 8.2.4).

   Booking channel:  In this version, a node records every booking made
      through TALK with via "claude" (Section 8.2.2), whatever
      agent.kind the caller declared, and the merchant is told the
      booking came through Claude.  With other assistants, that is
      wrong.  A merchant SHOULD read via as "an assistant" until a later
      version names the calling agent in it.

   Writes without confirmation:  Since version 0.3, no caller can book,



                           Expires 5 May 2027                  [Page 23]

Internet-Draft                    BATP                     November 2026


      change or cancel except through TALK, and the node's code carries
      out a write only on a confirm that names a proposal it returned,
      before the proposal expires (Section 8.2.1).  This holds for every
      caller, whatever its agent.kind, and no longer depends on what a
      bridge tells its assistant.  A misbehaving caller can still send
      confirm without asking the guest: the node cannot tell whether the
      guest agreed.  Idempotency keys and the rule that a proposal runs
      at most once prevent duplicate writes on retries, not unwanted
      ones.

   A language model reading untrusted text:  The merchant's agent that
      answers TALK is a language model, and message is text it cannot
      trust: the guest's agent may relay anything that a person or a web
      page told it, including instructions written to make the model
      book, cancel or reveal data (prompt injection).  A node therefore
      relies on its code, not on the model's instructions, for
      everything below.

   Confirmation of writes in code:  A write proposed through TALK runs
      only on a later confirm that names its proposal before it expires,
      with the arguments stored with the proposal (Section 8.2.1).  This
      check MUST be made by the node's code, never left to the model:
      the model has no tool that writes, so no output of the model alone
      can create, change or cancel a booking.

   Tools and merchant binding:  The merchant's agent MUST only be given
      the guest-side operations of its own merchant (checking
      availability, finding the guest's bookings at that merchant, and
      proposing a booking, a change or a cancellation), never merchant-
      side operations such as listing a day's bookings or blocking a
      slot.  The merchant MUST be bound by the node's code, from the
      request's merchant, and MUST NOT be an argument of any tool the
      model fills in, so that one merchant's agent cannot read or change
      another merchant's data, whatever the model is told.

   Website content:  The text crawled from the merchant's website MUST
      NOT enter the agent's prompt as such.  Only data validated against
      a schema and reviewed by the merchant before publishing may, and
      the agent's prompt marks it as data, not instructions: it was
      still taken from a website, which anyone who can edit that website
      controls.

   Conversation identifiers:  A conversation identifier is a capability:








                           Expires 5 May 2027                  [Page 24]

Internet-Draft                    BATP                     November 2026


      with it, and the token of the agent.id it is bound to, a caller
      can continue the conversation and confirm its proposal.  A node
      MUST make it unguessable and bind it to the merchant and the
      agent.id (Section 8.2.3).  A node and a bridge MUST NOT log
      conversation identifiers together with guest names at a level
      enabled in production, and SHOULD log a digest of the identifier
      rather than the identifier itself.

   Model output:  reply is written by a model and can be wrong.  A
      caller MUST NOT tell the guest that a booking was made, changed or
      cancelled unless reservation says so.  Before asking the guest to
      confirm, a caller SHOULD show them pending.summary, which the
      node's code builds from the proposal itself.

   Guest identity:  In this version, a booking belongs to whoever gives
      its guest name and reference.  Any authenticated caller that knows
      both can have it changed or cancelled through TALK, and RECALL
      returns the bookings of any name.  This is acceptable only in an
      experiment with trusted callers.  A deployment beyond that needs
      guest authentication, which a later version would define.

   Error messages:  error.message reaches people.  A node MUST NOT put
      stack traces, internal names or data of other guests in it.

   Fallback URLs:  A caller passes fallback_url to a person.  A caller
      SHOULD only offer https URLs, and a node SHOULD only send URLs on
      the merchant's own website.

13.  Privacy Considerations

   Guest names:  Guest names and party sizes are personal data.  A node
      SHOULD NOT write guest names to logs at a level enabled in
      production.  The reference implementation logs, for each request,
      the agent id, intent, merchant, status and latency, and nothing
      that names the guest.

   Preferences:  DISCOVER filters can reveal diet or religion (vegan,
      halal, kosher).  A node MUST NOT store them beyond the request or
      link them to a guest.

   Conversations:  TALK messages and replies are free text, and may
      carry guest names, preferences such as diet or religion, and
      anything else the guest said.  The same rule as for guest names
      applies: a node and a bridge SHOULD NOT write message or reply to
      logs at a level enabled in production.  Unlike DISCOVER filters,
      which a node does not keep, a conversation keeps what was said in
      it for as long as the node keeps the conversation: a node SHOULD
      keep a conversation no longer than it accepts messages in it, and



                           Expires 5 May 2027                  [Page 25]

Internet-Draft                    BATP                     November 2026


      SHOULD NOT link it to a guest beyond it.  A node that shows its
      merchant the requests it received shows the merchant what the
      guest's agent said.

   Recall:  As Section 12 says, RECALL returns the bookings of any name
      it is given, and for 24 hours the notices too: a notice names the
      merchant, the booking and its date.  Callers SHOULD only send the
      name of the guest they act for.

   Agent identity:  agent.id identifies software, not a person.  A
      caller SHOULD NOT put personal data in it.

Appendix A.  The MCP Bridge

   An MCP server can let an assistant that only speaks MCP use a BATP
   node.  The reference bridge opens one session with agent.id
   urn:batp:agent:claude-gateway and agent.kind user-agent, and maps its
   tools to intents:











                           Expires 5 May 2027                  [Page 28]

Internet-Draft                    BATP                     November 2026


    +=====================+=============+=============================+
    | MCP tool            | BATP intent | Notes                       |
    +=====================+=============+=============================+
    | search_merchants    | DISCOVER    |                             |
    +---------------------+-------------+-----------------------------+
    | talk_to_merchant    | TALK        | the tool's merchant becomes |
    |                     |             | the request's merchant      |
    +---------------------+-------------+-----------------------------+
    | get_my_reservations | RECALL      |                             |
    +---------------------+-------------+-----------------------------+

                    Table 11: MCP tools and BATP intents

   The tool talk_to_merchant(merchant, message, idempotency_key,
   conversation?, confirm?) passes its arguments other than merchant as
   the params of TALK, and returns the result of TALK.  Since version
   0.3, it is the only tool with which the assistant can check
   availability or book, change or cancel.  The reference bridge also
   serves one MCP endpoint per merchant, whose only tool is
   talk_to_merchant without merchant: the request's merchant is the
   endpoint's.

   *  The description of talk_to_merchant tells the assistant to relay
      reply, to show pending.summary and ask the guest when pending is
      set, to send confirm only after the guest's explicit yes to that
      summary, never in the same reply as the call that returned
      pending, and to give the guest any fallback_url.  That is how the
      bridge meets the caller's part of Section 7.8; the node's code
      enforces the rest.

   *  The tool takes a random UUID as idempotency_key, one per message:
      the bridge carries all its users under one agent.id, so their keys
      must not be guessable (Section 7.7).

   *  The bridge answers each tool call within 2 seconds, including the
      round trip to the node, except talk_to_merchant, which it gives 30
      seconds: longer than the node's deadline for TALK (Section 7.4),
      so that the node's 503 and its fallback_url arrive before the
      bridge gives up.  A timeout, a lost session or a 503 becomes an
      agent_unavailable tool error with the merchant's fallback_url.
      When the call carried confirm, the error adds that the write may
      have gone through, and that the assistant should check with
      get_my_reservations before sending the message again with the same
      key.

   *  The bridge carries the conversations of all its users on its one
      session, under one agent.id: only the conversation identifier,
      which the node makes unguessable (Section 8.2.3), keeps one user



                           Expires 5 May 2027                  [Page 29]

Internet-Draft                    BATP                     November 2026


      from continuing another's conversation.  A 404 for an unknown or
      expired conversation is a not_found tool error, not an outage: the
      assistant starts a new conversation.

   *  A status and its error object become the tool error {"error":
      code, "message": ..., "fallback_url": ...}. too_many_requests is
      not a tool error code: the bridge stays under the limit on
      requests in flight, and reports any 429, including one for a TALK
      beyond the node's limits on model use, as agent_unavailable.

Appendix D.  Changes from Earlier Versions

D.1.  Version 0.3

   *  Removed the intents AVAILABILITY, BOOK, AMEND and CANCEL: a caller
      checks availability and books, changes or cancels only through
      TALK.  A node answers them as unknown intents, with status 400 and
      code invalid_input, in a session of any version (Section 8).

   *  TALK is the only intent that takes merchant (Section 7).

   *  Stated what a confirmed proposal writes, and that a booking made
      through TALK is recorded with via "claude" whatever agent.kind the
      caller declares, since no token proves it; version 0.2 required
      "merchant" for a merchant-agent (Section 8.2.2).

   *  tools_called names the write that the node's code ran on a confirm
      (Section 8.2).

   *  No request is answered with status 409 or 413 any more; 413
      remains for frames above the size limit, and a later version
      cannot give slot_unavailable or party_too_large another meaning
      (Section 9).





                           Expires 5 May 2027                  [Page 46]

Internet-Draft                    BATP                     November 2026


   *  Idempotency keys are those of TALK only, scoped to the
      conversation; a key sent again with other params is invalid, and a
      caller that carries several guests chooses keys they cannot guess
      (Section 7.7).

   *  Confirmation of writes is enforced by the node's code for every
      caller (Section 7.8).

   *  While the major version is 0, a minor version may remove intents
      (Section 11).

   *  The MCP bridge maps three tools, and books only through
      talk_to_merchant (Appendix A).

D.2.  Version 0.2

   *  Added the TALK intent (Section 8.2), with its conversations and
      its proposals, which the node carries out only on confirm; TALK is
      addressed, so merchant is required for it.

   *  Stated how the session's version is chosen, and that a session of
      version 0.1 is neither offered nor served TALK (Section 11).

   *  Added deadlines for answering requests: 25 seconds for TALK, 10
      seconds for the other intents (Section 7.4).

   *  Added TALK to the idempotency rules, and said that a client
      library does not send a TALK again by itself (Section 7.7).

   *  Moved the reservation of event frames to a later minor version
      (Section 10).

   *  Added the bridge's talk_to_merchant tool (Appendix A).

   *  Added the security and privacy considerations of a merchant agent
      built on a language model (Section 12, Section 13).
