Let Claude book with any merchant, straight from their website.

BaselHack 2026 · restaurants first

The problem

Claude can find a restaurant.
It can't book a table there.

1

A website and a phone

Many small restaurants take bookings by phone, by email or through a form on their own site.

2

Nothing an assistant can call

No API and no tools. An assistant can only send the guest to the site and stop there.

3

No time to integrate

A restaurant won't build and run a server so that assistants can book with it.

The idea

A website and a few words in.
A booking agent out.

In

The merchant chats

The website's address and how the room works: 44 seats on 12 tables, groups up to 6.

Built

Sésame reads and builds

It reads the site and fills a validated profile with the hours, tables and rules. It then sets up the restaurant's own data and its booking tools.

Out

Claude books, the merchant sees it

Guests book from Claude through one connector. Each booking appears live on the merchant's management site.

Why it holds

Built so that a demo can't double-book

The guest says yes

Claude's tools tell it to show what it will book and wait for the guest's yes. A booking or a change carries an idempotency key, so a retry with the same key never books twice.

#14 · #109

One table, one time

A Postgres exclusion constraint on table and time range. Two bookings at once for the last table: exactly one wins.

ADR-0001

The LLM fills a form

It never writes code, SQL or tools. Its answer is validated, and every assumption is shown to the merchant.

ADR-0003

A way out

A slow or paused agent, or a group too large: the guest gets the restaurant's own booking page.

§8.4

Only who built it

A secret link, shown once, opens the management site. Only its hash is stored. On the server, a new build needs an invitation.
